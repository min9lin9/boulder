# Boulder Workflow Profiles

## TL;DR
> **Summary**: Promote Boulder from a GJC/LazyCodex executor harness into a workflow profile manager for Codex work. GJC + LazyCodex remains the default programming profile, while research, operations, critique, and compound workflows become swappable project profiles.
> **Deliverables**: profile schema, profile commands, current-profile state, profile-aware quickstart/doctor/pipeline/export, tests and CLI QA.
> **Effort**: Medium
> **Parallel**: YES - 3 waves
> **Critical Path**: schema -> commands -> surface updates -> verification

## Context
### Original Request
The user clarified that Boulder is needed because programming work should default to GJC planning on KIMI K2.7 and LazyCodex execution on GPT 5.5 medium, while critic and compound work must be independently runnable to reduce repeated planning effort. Boulder must also support non-programming Codex workflows such as research and operational work, reduce token usage, and allow workflow changes within the same project.

### 정반합 Review
- 정: Current GJC/LazyCodex default is useful because it gives Boulder an immediately valuable programming workflow.
- 반: If GJC/LazyCodex remain the product identity, Boulder becomes too narrow and cannot explain research, operations, critic, or compound workflows.
- 합: GJC/LazyCodex should become one built-in `programming-default` workflow profile. Boulder itself should own profile selection, switching, verification, and evidence.

### Metis-Style Gaps Addressed
- Current `executors` model lacks profile identity, model metadata, critic lane, compound lane, and saved profile state.
- `quickstart` currently treats GJC/LazyCodex as expected values, which makes custom profiles look like setup failure.
- Historical case-study evidence can be confused with current routing unless export records the active profile.

## Work Objectives
### Core Objective
Make workflow profile the first-class Boulder abstraction while preserving the current default GJC/LazyCodex programming path.

### Deliverables
- `.boulder/profiles/*.yaml` project profile storage.
- `.boulder/current-profile` active profile pointer.
- Built-in profiles: `programming-default`, `research-default`, `ops-default`.
- CLI commands:
  - `boulder profile list`
  - `boulder profile show [name]`
  - `boulder profile use <name>`
  - `boulder profile save <name>`
- Profile-aware `quickstart`, `pipeline`, `doctor`, and `export`.

### Definition of Done
- `bun test` passes.
- `bun run ci` passes.
- `boulder profile list --json` shows built-in and project profiles.
- `boulder profile use research-default` changes pipeline/export routing without editing `boulder.yaml` manually.
- `boulder doctor --json` distinguishes active profile adapters from unverified installation state.

### Must Have
- GJC is explicitly `Yeachan-Heo/gajae-code`.
- LazyCodex is an execution adapter preference, not a guaranteed dependency.
- Default programming profile includes model metadata: planner `kimi-k2.7`, executor `gpt-5.5-medium`.
- All live adapter commands remain approval-gated.
- External adapter handoff must be tenant-policy-safe by default: Boulder must not send private workspace files, raw diffs, secrets, local paths, or unredacted repo content to external models.
- External adapters receive an explicit handoff packet generated by Boulder, not arbitrary local files. The packet must declare data classification, redaction status, allowed destination, approval receipt, and evidence path.
- External model transmission is blocked by default. Boulder may generate and review sanitized packets by default, but it must not send packets to GJC, LazyCodex, or any external adapter unless the user gives explicit send approval.
- Raw workspace content remains forbidden even with send approval. Approval can authorize only a sanitized packet transfer, not arbitrary file passthrough.

### Must NOT Have
- No automatic GJC/LazyCodex install.
- No credential handling.
- No provider calls during profile switching.
- No claim that profile metadata proves adapter availability.
- No raw `@plans/*.md`, `@src/*`, or workspace file passthrough to external models as the default integration path.
- No default `handoff send`, provider call, `bunx gajae-code @file`, or `lazycodex run --repo .` behavior.

### External Handoff Safety Contract
External adapter integration must follow this state machine:

```text
packet -> review -> send
```

- `packet`: allowed by default; generates sanitized packet only.
- `review`: allowed by default; validates and displays packet contents only.
- `send`: blocked by default; requires explicit approval flag or approval receipt.
- `raw workspace`: always forbidden; never allowed as Boulder-managed external handoff input.

Default policy:

```yaml
externalAdapters:
  default: blocked
  requireExplicitApproval: true
  rawWorkspaceContent: forbidden
  sanitizedPacket: allowed-after-approval
```

### Profile Resolution Contract
Profile resolution is not a config merge. It is a local-only compile step that turns available profile sources into the workflow contract Boulder will use for the next command.

Resolution order:

```text
1. CLI explicit profile override
2. task-class suggested profile
3. .boulder/current-profile
4. boulder.yaml legacy executors
5. built-in programming-default
```

Important rule: task-class suggestion must never auto-use a profile. It can recommend `research-default`, `ops-default`, or another profile, but state changes require `boulder profile use <name>` or an explicit command override.

Required fixtures:

```text
fixtures/profiles/resolved/programming-default.json
fixtures/profiles/resolved/research-default.json
fixtures/profiles/resolved/ops-default.json
```

Each resolved fixture must include:

- `schemaVersion: "boulder.profile.resolved.v1"`
- `source`
- `id`
- `purpose`
- `surface`
- `lanes`
- `externalPolicy`
- `fallback`
- `drift`
- `suggestion`

Legacy migration example:

```yaml
executors:
  planning:
    preferred: custom-planner
    mode: detect-and-suggest
  execution:
    preferred: custom-executor
    mode: detect-and-suggest
  fallback:
    planning: codex
    execution: manual
```

must resolve to a generated legacy profile:

```json
{
  "schemaVersion": "boulder.profile.resolved.v1",
  "source": "legacy-manifest",
  "id": "legacy-boulder-yaml",
  "purpose": "programming",
  "drift": {
    "legacyExecutorsUsed": true,
    "differsFromBoulderYaml": false,
    "missingProjectProfile": false
  }
}
```

`profile resolve` stdout/stderr contract:

```bash
boulder profile resolve --json
```

prints the resolved JSON to stdout and writes nothing to stderr on success.

```bash
boulder profile resolve --task research
```

prints a human summary including active profile, suggested profile, source, and whether the suggestion was applied. It must say `suggestion-applied: false` unless the user explicitly selected that profile.

```bash
boulder profile resolve --profile missing --json
```

exits `1`, prints no stdout, and writes:

```text
ERROR profile.not_found: Profile "missing" was not found.
```

Drift warnings:

- `profile.drift.legacy-executors`: legacy `boulder.yaml.executors` generated the active profile.
- `profile.drift.current-missing`: `.boulder/current-profile` points to a missing profile.
- `profile.drift.manifest-differs`: active project profile differs from legacy `boulder.yaml.executors`.
- `profile.suggestion.not-applied`: task-class recommendation differs from active profile and was not auto-applied.
